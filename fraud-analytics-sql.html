Fraud Analytics com SQL

Uma fila de alertas não precisa ser apenas uma lista: este projeto usa comportamento transacional e SQL analítico para transformar sinais em prioridade operacional.

1. Da transação ao comportamento

Além de volume e ticket médio, o projeto compara cada transação com o histórico recente da própria conta e mede velocidade entre operações.

AVG(t.amount) OVER (
  PARTITION BY t.account_id
  ORDER BY t.transaction_date, t.transaction_id
  ROWS BETWEEN 5 PRECEDING AND 1 PRECEDING
) AS previous_5_avg
Uma transação é tratada como outlier quando o valor é pelo menos 3× a média das cinco anteriores.

2. Velocity

LAG(transaction_date) OVER (
  PARTITION BY account_id
  ORDER BY transaction_date, transaction_id
) AS previous_time

A investigação seleciona operações com intervalo de até 5 minutos e valor a partir de R$ 2.000, adicionando contexto temporal ao risco.

3. Score de alertas

(CASE WHEN risk_score >= 90 THEN 3 ELSE 0 END) +
(CASE WHEN amount >= previous_avg * 3 THEN 2 ELSE 0 END) +
(CASE WHEN gap_minutes <= 5 THEN 2 ELSE 0 END) +
(CASE WHEN hour BETWEEN 0 AND 4 THEN 1 ELSE 0 END)

O score combina risco prévio, desvio comportamental, velocidade e horário. Depois, converte a pontuação em P1, P2, P3 ou P4.

4. Resultado operacional

Priorização

46 operações P1/P2 representam somente 0,92% da base.

Exposição

Essas operações concentram R$ 490.281,62 em volume financeiro para análise prioritária.

O projeto não chama alertas de “fraude confirmada”. A lógica organiza sinais para investigação — distinção importante em prevenção a fraudes.

5. Camada para BI

CREATE OR REPLACE VIEW public.vw_dashboard_kpis AS
SELECT COUNT(*) AS total_transactions,
       SUM(CASE WHEN priority_level IN ('P1 - IMEDIATA','P2 - ALTA')
           THEN 1 ELSE 0 END) AS p1_p2_alerts
FROM public.vw_fraud_alert_queue;

A view transforma a análise em indicadores consumíveis por uma camada de dashboard.

Como o SQL investiga comportamento

Outlier vs. histórico recente

AVG(t.amount) OVER (
  PARTITION BY t.account_id
  ORDER BY t.transaction_date, t.transaction_id
  ROWS BETWEEN 5 PRECEDING AND 1 PRECEDING
) AS previous_5_avg

O projeto compara cada operação com a média das cinco anteriores da mesma conta e sinaliza valores a partir de 3× esse histórico.

Velocity

LAG(transaction_date) OVER (
  PARTITION BY account_id
  ORDER BY transaction_date, transaction_id
) AS previous_time

Outro sinal considera intervalo de até 5 minutos entre operações e valor a partir de R$ 2.000.

Score e decisão

(risk_score >= 90)          +3
(amount >= previous_avg*3)  +2
(intervalo <= 5 min)        +2
(horário entre 0h e 4h)     +1

A combinação vira uma prioridade P1–P4. O resultado principal foi 46 operações P1/P2 — 0,92% da base — concentrando R$ 490.281,62 para análise prioritária.

Insight: alerta de risco não significa fraude confirmada. O objetivo é ordenar sinais e concentrar capacidade investigativa.
